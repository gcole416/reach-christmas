PURPOSE OF THIS SESSION
  Walk the whole tool end to end, in the order the real drive happens:
  a family registers -> the school counselor confirms them -> staff
  imports them -> a sponsor claims a child -> the gift is tracked,
  checked, printed, and handed out.

  What we actually want out of the room today: does the FLOW make sense,
  and is the WORDING on the forms right. Everything else (colours,
  layout, missing reports) is a parking-lot item - write it down, keep
  moving. Grant will turn the wording feedback into user stories after.

  Everything you will see is fake demo data on the DEV site. Nothing here
  is on the real (production) site yet - that sync is a separate step.

------------------------------------------------------------------------
BEFORE YOU START   (do this ~15 min early, on your own)
------------------------------------------------------------------------

1.  START THE APP
      In a terminal, in the project folder:  cd web  &&  npm run dev
      It opens on   http://localhost:3000
      Leave the terminal running for the whole demo.
      "npm run dev" always points at the DEV Supabase project - good,
      that is what we want. (Production is only used by "npm run build".)

2.  TWO BROWSER WINDOWS, side by side, is the easiest way to run this:
      - Window A: signed in as an ADMIN  (testadmin@test.account)
      - Window B: a plain window with no login - this is your "family",
        your "counselor", and your "sponsor". They never log in.
      Later, for the privacy bit, you will sign Window B in as the
      VOLUNTEER account (testuser@test.account).
      You have both passwords.

3.  CHECK THE DEMO DATA IS THERE  (so you are not surprised live)
      Window A -> http://localhost:3000/admin  -> sign in.
      - Dashboard should show a handful of children and some sponsors.
        If it is empty, the demo seed has not been run on dev - stop and
        run the standard demo seed scripts before the meeting.
      - Open  http://localhost:3000/form/demo-north-family-2026
        You should see the family registration form for "Demo Elementary
        North". If you get a "link isn't active" page, the intake demo
        seed is not on dev.
      - Open  http://localhost:3000/review/demo-north-review-2026
        You should see the counselor roster for the same school.

      The two demo links (safe to type on a projector, they are fake):
        FAMILY FORM     /form/demo-north-family-2026
        COUNSELOR VIEW  /review/demo-north-review-2026

4.  ONE DECISION TO MAKE FIRST - which version of the form wording?
      The form has been reworded a few times recently. The newest changes
      (email now required, "OneLife Church" instead of "Reach Church" in
      places, a reworded confirmation screen) may or may not be live on
      the dev link yet.
      - If you want the room to review the very latest wording, re-run
        the existing intake form publish/seed script on dev first thing
        this morning. That does NOT add new demo data - it just re-points
        the demo link at the newest wording.
      - If you would rather not touch anything, just demo what is live and
        note "newer wording is coming" out loud.
      Either way: know which one you are showing before you walk in.

5.  THE SPONSOR EMAIL-CODE STEP - decide how you will handle it.
      When a sponsor claims a child, the app really does email them a
      6-digit code and makes them type it back. In the demo you have two
      options:
        a) Use a real email address you can pull up on screen (your own),
           claim a child for real, read the code, paste it in. Cleanest
           story, but depends on live email delivery in the moment.
        b) Fill in the sponsor details, click "Send code", show the
           "enter your code" screen, then say "in real life you'd get the
           code by email and type it here" and close it. Then point at a
           child in the grid that is already claimed to show the end
           state.
      Pick one. (a) is better if email is behaving.

6.  RESETTING BETWEEN RUNS
      Each practice run you do will leave a real (fake) submission on the
      dev site. That is fine - it is all tagged test data and there is a
      cleanup script. You do NOT need a clean slate to demo; a few extra
      rows in the queue actually make the "queue" look realistic.

THE 60-SECOND MAP   (say this before you click anything)
------------------------------------------------------------------------

  "Here is the whole life of one child's gift, start to finish:

     1. Staff send a school a registration link.
     2. The counselor forwards it to the families they've referred.
     3. A parent fills it out on their phone. No login.
     4. The counselor opens their own link, looks down the list, and
        confirms 'yes, these are real kids I referred.' They can fix a
        misspelled name. No login for them either.
     5. Staff click Import. THAT is the moment the household becomes real
        in the system - children, cards, everything.
     6. A sponsor goes to the public page, picks a child, claims them.
     7. Staff track the gift: pledged -> bought -> dropped at church ->
        checked against the wish list -> handed out.

   Old way: a Google form, a giant spreadsheet, and a volunteer retyping
   everything. New way: no retyping, and the counselor vouches for every
   family before it counts."

========================================================================
PART 10  -  THE SUPPORTING PAGES  (quick tour, 30 sec each)
========================================================================

SCHOOLS  (/admin/schools)
  Partner schools in this drive, each with a one-letter card code, a
  liaison contact, and a distribution method. Add-only for now (no edit
  or remove in the app).

DRIVES  (/admin/drives)   [admin only]
  One drive per year. Exactly one can be "Open" at a time - that's the
  one the whole app reads and writes. Draft -> Open -> Closed ->
  Archived. Also sets the default hand-out method and the referral
  window dates.

STAFF & PERMISSIONS  (/admin/staff)   [admin only]
  Everyone with a login, their role (admin or volunteer), and a
  "confidential access" toggle for volunteers who need to see
  confidential households without being full admins. New logins are
  still created in the Supabase dashboard, not here. You can't change
  your own role (so you can't lock yourself out).

AUDIT LOG  (/admin/audit)   [admin only]
  Every create / edit / delete across the system - who, when, and what
  changed. No export button, on purpose, because it can contain
  children's details.

HIGH SCHOOLERS  (/admin/high-schoolers)
  Grades 9-12 - the self-shopping bucket. A roster (filter by school,
  copy to a spreadsheet) and a board that walks each teen through
  not-contacted -> invited -> confirmed -> attended for the shopping day.

ON HOLD  (/admin/on-hold)   [admin releases; volunteers just see it]
  A child parked for duplicate review. While on hold, their card is out
  of the sponsor pool, the print run, and every count - nothing is
  deleted. An admin releases the hold once it's sorted.

PART 11  -  THE PRIVACY MODEL  (weave this through, or do it here)
========================================================================

Four kinds of people, only one of them logs in:

  STAFF / ADMIN     - full access, including confidential households.
  VOLUNTEER         - full access EXCEPT confidential households, unless
                      individually granted.
  SPONSOR           - public, no login. First name + grade + sizes +
                      wish list + specific needs, for unclaimed,
                      non-confidential kids only. Never a last name,
                      school, or address.
  COUNSELOR         - a link, no login. First name + age + grade for
                      their school's registrations. Nothing else.

CONFIDENTIAL HOUSEHOLDS:
  - Invisible to volunteers who haven't been cleared - not greyed out,
    genuinely not returned to them.
  - For cleared non-admins, the child's first name shows as an initial
    only ("C.").
  - Never appear on the public sponsor page under any circumstance.

DO - show it live:
  In Window B, sign in as the VOLUNTEER account and open Households.
  The confidential household ("Household Z1", child "Chloe" in the seed)
  is NOT in the list. Back in Window A, go to Staff & permissions, tick
  "confidential access" for that volunteer. Reload Window B - now the
  household appears, but the name shows as "C.".

SAY: "All of this is enforced in the database itself, not just hidden in
      the screen. A bug in the page can't leak a child's details,
      because the database never hands them over in the first place."
