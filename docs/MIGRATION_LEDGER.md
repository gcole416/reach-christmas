# Migration ledger

The source of truth for which database migrations are on which Supabase
project (US-51; closes OPEN_QUESTIONS DB-1 / DB-25 going forward). When a
migration is applied anywhere, update its row here in the same commit.
Migration file headers have their own "APPLY STATUS" notes; if a header and
this ledger disagree, **this ledger wins**.

- **Dev:** `thvyntrxmahygesltgft`
- **Prod:** a fresh project, to be created at launch (decided by Grant,
  2026-10-20). The old prod project (`mpiueduyrmplrueviupl`) is retired, not
  migrated: read-only probing on 2026-10-20 showed it had only part of the July
  schema (for example `is_admin` and `public_available_cards`, but not
  `request_claim_code` or `get_form`), with no record of what was applied.

Dev status was verified on 2026-10-20: every migration's feature is present on
dev (the e2e suite exercises all of them, and the five whose headers still said
"not yet applied" were checked directly: `review_tokens.token`,
`drive_schools.digest_paused`, `assignments.card_emailed_at`, and the
counselor-email tables). Earlier dev apply dates come from docs/backlog.md
where recorded.

Apply order is the filename order (timestamp prefix). For the fresh prod
project, all 34 are combined into
[`supabase/prod_bootstrap.sql`](../supabase/prod_bootstrap.sql) (one
transaction, empty databases only), generated by
`web/scripts/build-prod-bootstrap.mjs`. **When a migration is added or
changed, rerun that script** (`--check` tells you if the file is stale). On
2026-10-20 the combined file was run on an empty Postgres 17 (PGlite, with
stand-ins for Supabase's auth, Vault, pg_net and pg_cron): 510 statements,
22 tables, 4 views, 43 functions, row-level security on every table; then
`prod_setup.sql`; then the main workflow end to end (sign-up profile,
admin promotion, form publish, registration, counselor confirm, import,
sponsor assignment, review-link replace, email-off refusal), all passing.
See [PROD_LAUNCH_CHECKLIST.md](PROD_LAUNCH_CHECKLIST.md) step 2.
